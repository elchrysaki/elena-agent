# 2026-11-16 · AI memory: open systems store facts and when they were true, not the context of a taste

## Focus
Research question 5 (how AI systems store, retrieve, forget and consolidate memory). It follows the thread carried from the 14th and 15th: **does any open-source memory system store the *context* of a preference (season, neighbours, exposure, how it was produced), or only the fact?** If bi-temporal stores like Zep/Graphiti can already say "true in autumn", the agent could build on one instead of inventing its own store.

## Key findings
**Established (papers, docs, open code). Most numbers are from summaries and are marked where I could not check the primary text.**
- **Zep/Graphiti is bi-temporal.** Every fact is an edge with two timelines: when it was true in the world (`valid_at` / `invalid_at`) and when the system learned or retired it (`created_at` / `expired_at`). When a new fact contradicts an old one, the old edge is closed (its `invalid_at` is set to the new fact's `valid_at`), not deleted, so history can be replayed. Open source (Apache-2.0, `graphiti-core`). Benchmark gains: the reported numbers differ between summaries, so treat them as unverified. [Rasmussen et al. 2025, arXiv 2501.13956, review](https://www.themoonlight.io/review/zep-a-temporal-knowledge-graph-architecture-for-agent-memory); [Graphiti schema notes](https://zby.github.io/commonplace/agent-memory-systems/reviews/graphiti/)
- **Mem0 updates memory with four LLM-chosen operations: ADD, UPDATE, DELETE and NOOP.** A new fact is compared with its nearest stored neighbours, and the model picks one operation. The plain version *deletes* contradicted memories. The graph version (Mem0g) marks them invalid instead, which keeps history. Later work criticises merges and rewrites for *silent information loss* such as timestamp erasure and collapsed events. That critique is second-hand. [Chhikara et al. 2025, arXiv 2504.19413, overview](https://www.emergentmind.com/papers/2504.19413)
- **Generative Agents score retrieval as recency + importance + relevance, and reflect when importance piles up.** Recency decays exponentially per hour (γ≈0.995, reported). Importance is an LLM rating from 1 to 10. Relevance is embedding similarity. *Reflections* (higher-level insights) are written back into the same stream with links to the observations they rest on, and they are triggered by accumulated importance, not by a clock. The exact weights are disputed between write-ups. [Park et al. 2023, arXiv 2304.03442](https://arxiv.org/pdf/2304.03442v2)
- **Letta separates "think" from "remember".** A background *sleep-time agent* rewrites the primary agent's in-context memory blocks between conversations, so consolidation does not slow replies. This is the same fast-log plus slow-consolidation pattern as our weekly Sunday fold. [Letta, sleep-time compute 2025](https://letta.com/blog/sleep-time-compute); [Letta, memory blocks](https://letta.com/blog/memory-blocks)
- **Benchmarks show that *updated* and *implicit* preferences are the hard part.** LongMemEval tests knowledge updates and temporal reasoning separately, and finds that simple memory designs fail at time. Time-aware query expansion and storing facts with their session helped a lot. [Wu et al. ICLR 2025](https://arxiv.org/pdf/2410.10813) In PrefEval, models followed stated preferences under 10% of the time in long chats. In PersonaMem-v2, frontier models reached about 37–48% on *implicit* preferences, and the authors call reasoning, not storage, the bottleneck. [PersonaMem-v2, arXiv 2512.06688](https://arxiv.org/html/2512.06688v1)

**Answer to the carried question:** no system I found stores the *conditions* of a preference. Graphiti comes closest. Its validity interval can say *when* a like held ("Oct–Nov 2026"), but not *why* it might hold or fail: season, neighbours, exposure count, chosen vs rated, finish, or her language. All of the systems store a sentence-like fact. Context, if kept at all, survives only as free text inside that fact. **Speculation (mine):** this is the real gap for a taste agent. A time interval is not a condition. "True in autumn" is a *recurring* condition, while `valid_at` is a one-off span.

## What this means for the agent
1. **Never DELETE a taste.** Use Graphiti-style invalidation: close the old preference with `invalid_at` plus a `reason` (aesthetic | misread | scope | new info, same tags as the changelog). Mem0-style deletion erases exactly the first-ask→final-decision gap we learn from.
2. **Add a *conditions* field next to the validity interval**, e.g. `conditions: {season: autumn, neighbours: [...], exposure: 3, mode: chosen, finish: matte, lang: el}`. Retrieval filters on conditions as well as time. A like stays [I] until it is seen under a second set of conditions (the cold re-look and the other season from the 14th and 15th).
3. **Two clocks per item: `said_at` and `confirmed_at`.** The recency weight should run from the last *confirmation*, not from the first mention. This stops an old but re-confirmed love decaying under a new passing whim.
4. **Reflection is triggered by importance, not by the calendar.** Keep the Sunday fold, but also fire a consolidation when several high-importance signals pile up: swearing or "bro", "lock it", a rollback, or an overturned preview. Write reflections back with links to their evidence, so a rule can be traced and later retired.
5. **Use separate scores, not one blended relevance score:** `recency(confirmed_at)`, `importance` (her emotional weight: words like "love", "hate", "never"), `relevance`, plus `condition_match`. The blend can be tuned per task: visual work weights condition_match highly, scope rules weight importance.
6. **Keep the raw log forever and keep the profile small.** Merges lose detail (the Mem0 critique). The changelog is the episodic store. design.md, voice.md and mistakes.md are compressed views that can be rebuilt from it at any time.
7. **The hard part is inference, not storage** (PersonaMem-v2). Spend effort on the step that turns "this feels cardboard" into a spec, and on asking one good question, not on a fancier database.
8. **Build on, don't rebuild:** Graphiti (local, Apache-2.0) is a fair base for the store. Add a `conditions` node type and an `[C]/[I]` confidence on edges. An MCP server on top gives the minimal-token sync.

## Applied to Elena
- [I] **Her profile already behaves like a bi-temporal store, but one that overwrites.** The weekly consolidation folds the changelog and clears it. If old entries are not archived, the "she wanted loud yellow in August" → "velvet near-black in November" path disappears, and the seasonal test planned for spring 2027 loses its baseline. Suggestion: archive each cleared changelog to `changelog-archive/YYYY-WW.md` instead of only clearing it.
- [I] **Her highest-importance signals are explicit and easy to detect** ("never break the palette", "lock it", swearing). That makes her a good fit for importance-triggered reflection. One "come on" probably carries more weight than ten mild approvals.

## Out-of-the-box connection of the day
**Graphiti's "invalidate, don't delete" is how she treats design versions.** Her standing rule is "keep A, make this B; never overwrite; keep variants switchable until I pick." That is a bi-temporal store of her own work: old versions stay valid in their own timeline, and a choice closes one branch without erasing it. The agent should store *her taste* the way she stores *her designs*. She already chose the memory model the agent needs, in a different domain. [I]
